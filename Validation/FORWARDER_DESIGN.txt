VALIDATION — FORWARDER DESIGN
Version: 0.1
Status: Living Design Document

1. PURPOSE
The Forwarder is the final delivery service in the Validation pipeline. It receives completed output from the processing/XML stage and reliably transfers it to the configured downstream system.

Pipeline boundary:
FINAL DATA/XML -> FORWARDER -> DOWNSTREAM SYSTEM

The Forwarder is not the Data Router. The Router handles source ingestion and Parser routing; the Forwarder handles final outbound delivery.

2. FUTURE INPUT
The normal future flow is:
Data Router
-> Data Parser
-> Normalization
-> Validation
-> Correlation
-> Reference Enrichment
-> Fusion
-> Final Data
-> XML Generator
-> Forwarder

The Forwarder should consume finalized XML/output and should not alter vessel/business content.

3. OUTPUT
The project has an established requirement for forwarding generated XML to a downstream destination. The earlier design uses SSH/SFTP-style delivery to a configured remote IP/port/path, with reliable processing/sent/failed handling.

Exact downstream protocol, IP, port, credentials and remote path must come from configuration/project specification. Never invent or hard-code them.

4. DELIVERY MODEL
Recommended generic flow:

FINAL OUTPUT
-> pending queue
-> Forwarder
-> remote connection
-> transfer
-> acknowledgement/success confirmation
-> SENT/DELIVERED state

On failure:
-> retry
-> remain pending
-> after retry exhaustion -> FAILED with reason

Do not delete final output merely because delivery failed.

5. FILE/OUTPUT STATES
Possible states:
GENERATED
PENDING
QUEUED
TRANSFERRING
DELIVERED
RETRYING
FAILED

Use persistent operational state so restart does not blindly resend already confirmed deliveries.

6. TRANSPORT
Support the actual downstream mechanism specified by the project. The known planned mechanism is secure remote file transfer using SSH/SFTP semantics.

Separate:
- connection management
- authentication
- transfer
- acknowledgement/verification
- retry
- state management

Credentials must never be stored in source code or logs.

7. RELIABILITY
Handle:
- remote unavailable
- connection timeout
- authentication failure
- transfer interruption
- remote disk/path error
- duplicate output
- local file missing
- local disk full
- service restart

Use configurable retry/backoff.
Do not endlessly retry permanent configuration/authentication errors without recording the condition.

8. INTEGRITY
Before marking delivered, verify the transfer according to the actual protocol, for example successful remote transfer and/or agreed acknowledgement.
Where appropriate, preserve filename, checksum or message ID to support duplicate protection and auditability.

9. QUEUE
Use a controlled/persistent pending queue.
Do not introduce a distributed message broker without a demonstrated requirement.
The Forwarder must tolerate temporary downstream outages without losing finalized output.

10. CONFIGURATION
Destination must be configuration-driven:
- destination name
- protocol
- remote host
- remote port
- remote path
- authentication reference
- enabled/disabled
- retry policy
- timeout
- polling/transfer mode as required

The Web Control Console will later manage these settings.

11. LOGGING
Log:
- output/message ID
- filename
- destination
- connection status
- transfer start
- transfer success
- retry
- failure reason
- timestamps

Never log passwords/private keys/secrets.

12. MONITORING
Track:
- pending count
- transferred count
- failed count
- retry count
- current connection state
- transfer rate
- last successful delivery
- last error
- queue depth

These will later be exposed to the Web Control Console.

13. SERVICE
Run as a long-running Linux service, eventually:
validation-forwarder.service

Support graceful shutdown and restart recovery.

14. OFFLINE/ON-PREMISE
The environment is primarily offline/on-premise. The Forwarder must not depend on cloud delivery services or Internet APIs.

15. DATABASE/STATE
PostgreSQL is the central application repository, but operational Forwarder state should remain appropriately separated from vessel/business data. A lightweight local state database is acceptable where needed for delivery tracking.

16. SECURITY
Use secure transport where required by the downstream specification.
Use externalized credential references.
Restrict filesystem access.
Validate remote paths/configuration.
Do not execute arbitrary shell commands based on filenames or configuration values.

17. TESTING
Test:
- successful delivery
- remote unavailable
- timeout
- authentication/configuration failure
- interrupted transfer
- retry
- duplicate prevention
- restart/recovery
- missing output
- disk full
- multiple destinations if later required
- large output files

18. CURRENT SCOPE
Forwarder architecture and interface are planned now. Implementation will be done after the upstream Parser/Validation/XML pipeline is established, unless explicitly instructed otherwise.

19. IMPORTANT BOUNDARY
Forwarder receives finalized output and delivers it.
It must not parse AIS, perform vessel correlation, enrich reference data, decide XML values, or modify business content.
