VALIDATION — FORWARDER DESIGN
Version: 1.0
Status: Implemented on feature/data-forwarder

1. PURPOSE
The Forwarder is the final delivery service in the Validation pipeline. It receives completed XML output from the Parser and reliably transfers it to the configured downstream system.

Pipeline boundary:
FINAL DATA/XML -> FORWARDER -> DOWNSTREAM SYSTEM

The Forwarder is not the Data Router. The Router handles source ingestion and Parser routing; the Forwarder handles final outbound delivery.

2. IMPLEMENTED FLOW
Data Router
-> Data Parser
-> Normalization / Validation / Correlation / Reference Enrichment / Fusion
-> XML Generator
-> atomic XML spool
-> Data Forwarder
-> configured destination

The Parser creates the finalized XML and atomically renames it into `Validation/Data_Forwarder/spool/pending`. The Forwarder consumes only complete `.xml` files and does not alter their content.

3. OUTPUT / TRANSPORT
The implementation supports configuration-driven `filesystem` delivery for offline testing and `sftp` delivery for the planned secure remote-file-transfer mechanism. Production host, port, remote path and credential reference remain deployment configuration and are not hard-coded.

4. DELIVERY MODEL
PENDING -> TRANSFERRING -> DELIVERED
Failure -> RETRYING -> DELIVERED or FAILED

A failed delivery leaves the finalized XML in the pending spool. Confirmed delivery is persisted in the Forwarder state database before the source file is archived.

5. DUPLICATE PROTECTION
Each output is identified by deterministic filename plus SHA-256 content digest. Delivery state is keyed by output ID and destination. A destination already confirmed as DELIVERED for the same digest is not retransmitted.

6. STATE
SQLite is used only for lightweight Forwarder operational state. It contains destination, checksum, filename, state, attempts, error and timestamps. Vessel/business data is not stored in this state database.

7. RELIABILITY
The service handles unavailable destinations, timeouts, authentication/configuration errors, transfer failures, restart recovery, duplicate output and missing destination configuration. Retry count and backoff are configurable.

8. INTEGRITY
Local delivery uses a `.part` file followed by atomic rename. SFTP uses a remote `.part` file, size verification when enabled, and rename to the final filename. Secrets are never written to source code or logs.

9. CONFIGURATION
`Validation/Data_Forwarder/config/forwarder.yaml` controls:
- enabled destinations
- protocol
- host
- port
- remote path
- username
- private-key file reference
- connection timeout
- transfer verification
- retry policy
- polling interval
- state/spool paths

10. MONITORING
HTTP endpoints are provided by the Forwarder:
- `/health`
- `/metrics`
- `/deliveries`

11. SERVICE
Systemd unit: `Validation/Data_Forwarder/systemd/validation-forwarder.service`.

12. OFFLINE / ON-PREMISE
No cloud or Internet delivery dependency is introduced. Paramiko is an optional installed dependency for the configured SFTP transport and must be supplied through the approved offline package repository.

13. SECURITY
SFTP host keys are loaded from the system known-hosts database and unknown hosts are rejected. Credentials are externalized. Remote paths are configuration values and no shell commands are executed from filenames/configuration.

14. TESTING
The Forwarder test suite covers successful filesystem delivery, disabled destinations, persistent delivery state and duplicate prevention. SFTP integration must be exercised against the actual deployment endpoint when its approved host/path/credentials are supplied.

15. CURRENT SCOPE
The Forwarder service is implemented. The exact production destination remains a deployment input because the project specification does not define a real downstream IP, port, remote path or credential reference.

16. IMPORTANT BOUNDARY
Forwarder receives finalized XML and delivers it. It does not parse AIS, perform vessel correlation, enrich reference data, decide XML values, or modify business content.
